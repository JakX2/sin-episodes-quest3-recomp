# Phase 1638: Concrete owner-held GameEnts lifetime registry

Stacked on all-green Phase 1637 PR #1645. Original retail GameEnts interface registration remains disabled.

The previous bounded vtable took owner callback pointers but did not ship a concrete owner-lifetime implementation. A caller could make every validator return true. This phase implements a reusable, fixed-capacity host-side registry for edict/entity/unknown/touch address identities, original PE32 minimum read extents, transmission-table candidate bindings and generation turnover. Its methods operate only on opaque addresses and owner-provided metadata, never dereference or execute original game objects.

Registration occurs only outside a dispatch lease. The registry records monotonically increasing 64-bit owner generations across address reuse in the same or different slots, refuses duplicate concurrently live addresses, and refuses relabeling an active transmission slot. A successful exclusive lease has a unique nonzero token and is tied to its owning thread and one of the six operational GameEnts vtable slots. Every validation requires that same thread/lease. Wrong-token or wrong-thread End does not unlock. Candidate records retain the original table token/index and the owner generation at binding time; retired or reused addresses remain unauthorized until the trusted owner explicitly binds a new generation.

Only slot 3, FreeContainingEntity, can retire a live entity during a lease. Retiring immediately denies entity, unknown, touch, pair and candidate validation but keeps the already-owned edict prefix addressable through release cleanup. The owner must subsequently call ForgetEdict after the lease to terminate that memory-ownership authorization. Enroll, ForgetEdict and BindCandidate are denied during all leases. This is independently authored lifecycle bookkeeping, not a reconstruction of actual retail edict allocation.

An original-free standalone C++ test exercises positive and negative enrollments, bounded storage sizes, exclusive lease tokens, cross-thread misuse, nested lease refusal, slot-3 retirement, edict retention, explicit forgetting, stale-generation address reuse, cross-slot migration, transmit candidate tombstoning and rebind. It is registered as a native Windows MSVC x86 CTest alongside the existing seven-slot GameEnts vtable, increasing the expected independent Win32 test count from 239 to 240.

TRUST BOUNDARY: This registry is usable by a host adapter only after independently authenticating the real engine allocator, owner-thread discipline, original memory extents and genuine generation counter. An untrusted caller can lie when enrolling identities. std::mutex protects registry metadata only, not retail engine memory. Neither Android gameplay nor retail Windows startup is demonstrated by this standalone registry. Original binaries were not committed.

## Authenticated engine edict stride update

Direct independent examination of the SHA-pinned original 2006 engine.dll (SHA-256 f3add5b41300e6d709fd0b492bfcdd37b9b3d20d9744f874c0b860bf021cec81) at VAs 0x20110E92 through 0x20110EA1 shows the edict array address is base + index * 0x14. The same original cleanup paths at 0x20110E50 and 0x20110EA9 clear state flag bit 1, invoke the GameEnts +0x0C FreeContainingEntity slot, then write zero at edict+0x10 and 0xFFFFFFFF at edict+0x04. The host registry now requires the entire 0x14-byte original edict element, and the synthetic x86 edict fixture has matching offsets and size. This is not a claim that the real retail engine allocator is already connected to the diagnostic object.
