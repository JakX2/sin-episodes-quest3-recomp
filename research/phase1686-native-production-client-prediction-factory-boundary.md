# Phase 1686: first native production VClientPrediction001 factory boundary

## Why this fixes a real engine-loadable gap

The original 2006 PE32 *engine.dll* requests the literal **`VClientPrediction001`** from the **client module's `CreateInterface`** during client-side startup, then invokes its **virtual slot1** with the authentic no-argument MSVC `__thiscall RET0` ABI. Source-attesting audit `research/tools/audit_sin_original_client_prediction23_abi.py` already verifies the full original engine and client images, original factory/version label and 50-byte engine factory-call window at `0x20023CF2`, original prediction singleton factory, constructor, 23-slot vtable, original slot1 `0x24195F80`, original `cl_predict` ConVar registration and direct parent numeric field reads.

The independently authored *production* `pc/independent_slot0/slot0.cpp` already provided `VClient011` and its **21 source-authenticated engine-app-system factory requests**, but **categorically refused `VClientPrediction001`**. Phase1685's verified **316/316 native Windows original-free tests** exercised the prediction state and reinitialization logic only inside independently compiled fixture executables. The factory mismatch remained a real engine integration blocker.

Phase1686 makes a first strictly limited change to that *production* boundary: the same actual replacement `client.dll` may now return a native `VClientPrediction001` singleton, but **ONLY** in a user-authorized owner diagnostic launch when `SIN_INDEPENDENT_CLIENT_PREDICTION_FACTORY_PROBE=1`, `SIN_INDEPENDENT_TRACE_FILE=1` and a validated 32-character lowercase hex `SIN_INDEPENDENT_TRACE_SESSION` are all set. Otherwise the published module continues refusing the interface, as before.

### Actual native `VClient011` startup behavior

1. The default `VClient011` slot0 still queries its existing 21 source-authenticated factory names, refuses missing inputs and returns failure. Existing owners and tests are unaffected.
2. With the opt-in gate and all 21 named services returned, the production code uses the **already acquired** `VEngineCvar002`, calling its pre-verified **virtual slot3 `FindConstVar("cl_predict")`**. There is **no** registration, mutation, command override or invented engine-owned object.
3. It reads the returned ConVar's original `m_pParent` pointer at **ConVar+0x18**, and **that parent's numeric DWORD+0x2C**, matching the full-SHA-authenticated original prediction slot1, not the queried alias's own integer. Both reads are preceded by bounded Win32 `VirtualQuery` committed/readable-page checks; missing/forged addresses refuse safely. The numeric value is **copied** into the independent prediction owner rather than retaining any arbitrary external source pointer.
4. Only after that real native factory acquisition succeeds does the owner update the gated singleton and let **`VClient011::Init` return 1**. This intentionally moves the original game engine into its next interface negotiation window for an explicit diagnostic session. Neither the asset pipeline nor remaining engine callbacks are implemented by this success, and no default configuration advertises startup.
5. The same real exported `CreateInterface` now returns the exact same process-lifetime singleton for `VClientPrediction001` under the session + successful-binding gate. Wrong versions `VClientPrediction002` and unrelated still-unimplemented interfaces remain rejected. `VClient011::Shutdown` revokes the binding and factory advertisement.
6. The singleton's actual compiler-generated MSVC Win32 x86 virtual table has the **23 original interface slots**. Source-authenticated slots1 (cached cl_predict BOOL at this+0x10), 2 (empty shutdown), 7 (three DWORD reset at +0x24/+0x28/+0x2C), and 15/16/17 (typed tiny field getters) are implemented. The original slot0 is a **deleting destructor**: because this singleton is retained through the engine session, an unexpected delete is refused rather than freeing the instance.
7. All other slots (3,4,5,6,8–14,18–22) are **deliberately terminal** and call the existing production `stopUnsupported` with a diagnostic. In particular, do not misread the original-free Phase1685 prediction lifecycle fixtures as engine-ready slot6 reconciliation: they still require unavailable entity and prediction callbacks.

The user-excluded physics/surface/model/prop features are neither expanded nor changed in this phase.

## Actual DLL-bound integration regression

New `pc/independent_slot0/test_client_prediction_factory_boundary.cpp` invokes Windows `LoadLibrary` against the real **built independent `client.dll`**, finds `CreateInterface` through `GetProcAddress`, and then calls the **actual returned native interface vtables**. Its fabricated `VEngineCvar002` implements the first five original ABI slots and owns a synthetic `console_abi::Variable`, including a valid ConVar parent pointer and numeric value at authentic +0x18/+0x2C. This test never loads retail SiN DLLs or an untrusted game asset.

The test checks: default/invalid-session/no-prior-Init refusal; original 21 engine factory acquisition order; absent `cl_predict` refusal; first successful owner-only `VClient011.Init` return; exact `VClientPrediction001` singleton identity; all 23 virtual entries inside the actual loaded replacement client DLL; actual native slot1/2/7/15/16/17 ABI and stack balance; changed ConVar integer; linked parent numeric behavior; forged ConVar pointer refusal; ordinary `VClient011.Shutdown` revocation; wrong interface-name refusal; and **child-process invocation of unsupported prediction slot3** proving deterministic terminating exit `0x53494E45` rather than a guessed return or stack cleanup.

One new CTest `independent_client_prediction_factory_actual_dll_native` is registered against the actual PE32 `sin_slot0_client` target. Previous Phase1685 exact-head verified **316/316** Windows MSVC x86 tests and all six workflows. Phase1686 targets **317** original-free tests, pending the exact-head CI result. Test pass does *not* prove actual game engine execution, startup or gameplay.

## Remaining original-game integration

This is a deliberately constrained interface-bounded advancement, **not** release of a playable reconstructed client. A real Windows game boot still needs engine-owned `VClient011` lifecycle callbacks beyond its 21-query prefix and full `IPrediction` game-facing slots (especially slot3/slot4/slot5/slot6), independent entity ownership and packet reconciliation services. It also needs real retail engine startup and boot evidence from the owner environment. The opt-in factory's numeric ConVar value is a *snapshot* suitable for original slot1 initialization, not the continuous live value needed for later game-frame prediction. No original machine code has been copied into this repository.
